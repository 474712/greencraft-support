一、验证方法与可复现性

1.1 为什么这份报告是可信的

智能体类参赛作品最常见的问题是"演示很好看，但说不清它到底准不准"。本项目采取的做法是：把测试直接架在生产产物上。

线上产物 index.html 是一个零依赖的单文件应用，测试代码不重写、不复制任何业务逻辑，而是在运行时把其中的 <script> 块抽取出来，在 Node 的最小 DOM 桩中执行，直接调用线上真实的 detectIntent / detectProduct / findKBResponse / findFuzzyScored / generateResponse。因此"测试用例与实现脱节"这一类问题在本项目中结构性地不可能发生。

1.3 复现命令

# 2) 留出集泛化验证（72 条）
node tests/run-tests.js --set holdout.json

# 3) 生成本报告的全部数字（输出 metrics-summary.json 与本文件的数据源）
node tests/metrics.js

三条命令均无需安装任何依赖（仅需 Node ≥ 16），且直接读取仓库中的 index.html。

  • 意图 6 类：故障诊断 / 养护保养 / 配件订购 / 保修咨询 / 选型对比 / 安全规范。

时延口径：计时区间只包含 generateResponse()——线上一次请求的完整决策链（意图识别 → 品类识别 → 知识检索 → 置信度判定 → 答复生成），不含为人工标注比对而做的重复检测。测量前先预热代码，再清空以文本为键的归一化缓存，使每一轮都是"引擎已热、问题全新"的真实场景；重复 3 轮取均值居中的一轮作为对外口径。本机实测均值区间 0.05–0.07 ms，三轮原始值见 tests/report/metrics-summary.json 的 engineLatencyMs.rounds。

⚠ 两类时延不可混用 引擎决策时延（0.05 ms）是性能指标，衡量系统本身的决策成本；端到端时延（802 ms / 3065 ms）是体验指标，包含了产品刻意设计的拟人化节奏——思考停顿 360–1200 ms（带随机抖动）+ 逐字流式呈现 14 ms/步。后者的数值随答复长度变化，是"让用户觉得对面是个人在打字"的设计投入，不是性能问题。答辩时若被追问"为什么 0.05 ms 的引擎要等 800 ms"，标准回答即在此。

为什么把这张对照表放进报告 智能体作品的可信度不来自"我做得很好"，而来自"我知道自己哪里做得不好，并且能量化地改进它"。上表的每一项改进都对应探针集上可复现的失败用例，而非主观优化。node tests/metrics.js 每次运行都会自动复测这一组探针，因此任何回归都会立即暴露。

8.3 其他可现场验证的特性

  • 零外部请求：浏览器 Performance 资源条目为空，无第三方脚本、无字体 CDN、无埋点。
  • 字体本地兜底：字体以 base64 内嵌为 woff2，同时配置系统字体栈，断网环境下排版不塌。

十、结论

在可复现的回归口径下，GreenCraft Pro 的意图识别准确率 100%、品类识别准确率 100%、知识库命中率 100%、一次解决率 98.6%，三类流程探针触发率均为 100%，单次引擎决策 0.05 ms（P95 0.10 ms），且全程零外部网络请求。

比数字更重要的是这些数字的可核验性：测试直接运行在生产产物上，脚本随代码提交，任何人执行三条命令即可复现全部结论；对无法在本阶段实测的指标，本报告选择留白而非填充估算值。

这一取舍本身即是本作品对"OPC 智能体"命题的回答——在售后这类答错代价不对称的场景里，一个能被审计、能被证伪、能被部署到客户自己服务器上的智能体，比一个更能"自由发挥"的智能体更有商业价值。
