一、项目背景与赛道定位

⚠ 全文口径声明 本文档严格区分四类信息，并在正文中逐一标注： 已实现＝可直接在演示原型中复现； 规划中＝路线图内的下一阶段，当前不可演示； 实测＝由可复现脚本跑出的真实数字； 测算＝基于行业基准的推算值，非本系统实测值。 凡未标注"实测"的数字，一律不得在答辩中表述为"我们已经做到"。

1.1 行业痛点与市场机会

园林电动工具（草坪修剪机、电动修枝剪、电链锯、绿篱修剪机、高压清洗机、割灌机、微耕机、碎木机、吹叶机、智能割草机器人）是中国出海占比最高的机电品类之一。与一般消费品不同，这类产品具有三个硬特征，直接决定了售后服务的形态：

  • 故障即咨询。用户购买后最常发生的动作不是"退货"，而是"启动不了 / 没劲 / 异响 / 漏油"。这类问题占售后的绝大多数，且多数可由用户自行解决——前提是有人告诉他怎么排查。
  • 语言即门槛。终端市场分布在欧美本地化电商渠道，同一品牌要面对英、法、德、西、意、荷、葡多套语言与多套安全规范（CE / ANSI / EN 等）。
  • 时区即成本。中国与欧美主要市场存在 6–12 小时时差，人工客服不可能覆盖 24 小时，排班成本与响应时延同时被放大。

本项目把"多语种 + 全时段 + 低成本"这三个约束同时作为硬指标，用一套可离线运行的规则引擎解决，目标是让中小型出海品牌用一台电脑、一个文件就能开出一条 8 语种售后通道。

1.3 设计目标与取舍原则

面对"要不要上大模型"这一选项，我们先明确本项目要解决的是售后知识路由问题，而非开放域生成问题。据此确立四条取舍原则：

  1. 可核验优先于生成质量。售后回答错一条代价极高（可能导致损坏或安全事故）。规则引擎的每一条结论都可回溯到命中词与知识条目，能被审计。
  2. 可离线优先于能力上限。出海品牌的客服数据涉及订单与设备信息，纯前端方案意味着数据不出浏览器，从根上规避数据合规成本。
  3. 可解释优先于流畅度。我们把引擎内部的判定依据直接展示给用户与运营，这既是产品特性，也是本赛道"智能体自主决策可解释"命题的直接答案。
  4. 实测优先于宣称。凡是能测的数字一律用脚本跑出来并公开复现命令；不能测的（如 CSAT、真实退货率）明确写为"需企业试点采集"。

二、系统架构与技术实现

2.1 总体架构

系统采用四层结构，全部逻辑与数据封装在单个 HTML 文件中，浏览器解析即运行，无构建步骤、无运行时依赖、无网络请求。

交付形态的关键含义 四层全部位于同一个 HTML 文件中：不需要 Node、不需要 npm、不需要构建工具、不需要后端、不需要 API Key。评委可直接双击打开 index.html，或访问已部署的线上地址。这既是"落地可行性"维度的直接证据，也决定了本方案在中小客户处的部署成本接近于零。

2.3 文本归一化与拼写纠错

所有匹配都建立在归一化文本之上，顺序不可调换：

  1. 小写化：消除大小写差异。
  2. 拼写纠错（TYPO_MAP）：覆盖售后场景高频手输错误与 OCR 错误，如 wont start → won't start、shoud → should、batery → battery。
  3. 音标折叠：法语 ça、德语 ä/ö/ü、西班牙语 í/ñ、葡萄牙语 ã/ç 等统一折叠为基础字母，德语 ß → ss。这样同一套词表可同时覆盖带音标与不带音标两种输入习惯。

词边界匹配采用 Unicode 属性类 (?<![\p{L}\p{N}])…(?![\p{L}\p{N}])，对拉丁语种按词边界命中（避免 person 误中 personal），对中日韩字符按包含匹配。匹配正则按词条缓存，避免重复编译。

2.4 意图识别：加权评分算法

每个意图在每个语种下维护一张强特征词表与一张弱特征词表（共 48 张表、1939 条词条）。识别时对用户文本逐条比对并加权累加：

  • 强特征：最长匹配 × 3.0，其余命中 × 1.0；
  • 弱特征：每条 × 0.4；
  • 最终得分最高者胜出；只有弱特征命中而无强特征时，不判定意图（转由澄清机制处理）。

"最长匹配 × 3.0"的用意是抑制短词淹没长词：start 与 won't start 同时命中时，后者应当主导判定。弱特征低权重的用意是保留"用户在描述问题但信号不足"的状态，交由主动追问而非强行作答。

为什么不用大模型做意图识别

售后意图是封闭标签集（6 类），且每类都有可枚举的判别特征。用模型去做一个封闭分类问题，等于用不可核验的手段解决一个可核验的问题。更重要的是：售后场景下"漏判"（该转人工却硬答）与"误判"（该走故障却走了配件）代价不对称——前者会造成安全事故。因此引擎采取宁可追问、不可硬答的策略：证据不足时主动反问，绝不编造。

2.5 品类识别与型号解析

品类识别独立于意图识别，输出三路证据并加权：

  • 产品关键词命中：最长关键词 × 3.0，其余 × 1.0；
  • 型号编码命中（如 GC-480E、LM2100SP、GC-2000PW）：直接 +100，可同时确定品牌与品类；
  • 产品系列命中（如 P-500、Pro P-800）：+30。

由于当前状态（state.context）在多轮中保持，用户的追问（"I tried charging it but still nothing"）即使不再重复产品名，也能继承上一轮的品类，不会掉入通用兜底。

2.6 知识检索链路

知识库以 KB[意图][品类][语种] 三维组织，每条为一组问句与答复（{q, a}）。检索分两级执行：先在「意图 × 品类 × 语种」单元内对全部候选条目打分排序——命中且置信度达标则直接答复，命中但置信度不足则发起澄清追问（挂起等待用户确认），单元内无候选时再沿「同语种通用 → 默认 → 英文回落」三级降级链兜底。每次实际命中的档位都会记录在「判定依据」卡片的「检索方式」一行：

模糊检索对中文采用二元组（bigram）重叠度，对拉丁语种采用词边界重叠度，置信度 = 命中片段数 / 分母，条目得分 = 基础分 × (1 + 置信度 × 0.5)。该链路保证：在 241 条条目规模下，任何一个能判定意图的问题都能命中至少一条同语种条目。

2.7 交互层与决策透明化

本项目区别于普通客服 Demo 的一个设计：每条机器人答复下方都附一张「判定依据」卡片，展示引擎的内部决策链路：

  • 命中的强特征原文（如"无法启动""won't start"）；
  • 命中的弱特征（如有）；
  • 识别出的品类；
  • 识别出的型号（如 GC-480E）；
  • 检索方式：精确命中 / 模糊命中 / 同语种通用条目 / 默认条目 / 英文回落 / 澄清追问 / 冷启动问候 / 触发转人工规则；
  • 置信度百分比。

这一设计把智能体的决策过程从"黑箱"变成"可审计对象"，同时也是演示中最有说服力的一段——评委可以指着任意一条答复追问"它为什么这么答"，答案就在卡片里。

2.8 工程化与可复现性

测试与指标生成脚本随代码提交，直接抽取线上 index.html 中的 <script> 块在 Node 中执行真实引擎函数，不做任何 mock：

3.1 八语种全链路覆盖

3.3 十个产品品类

产品谱系覆盖 10 个品类：草坪修剪机、电动修枝剪、电链锯、绿篱修剪机、吹叶机、高压清洗机、割灌机、微耕机、碎木机、智能割草机器人。界面顶部的分类筛选条可直接锁定品类，配合品类级知识条目，使答复精度从"通用建议"提升到"该型号的料号与参数"。

3.4 故障分诊与主动追问

当用户描述故障但未指明品类时，系统不再笼统回答，而是给出跨场景五路分诊并反问关键信息：

  • 供电（电池是否充满、是否插到位）；
  • 安全开关（安全钥匙、扳机开关是否同时到位）；
  • 异物（刀片/链条/叶轮卡草、树脂、石子）；
  • 过热（重载后需 15–20 分钟冷却）；
  • 磨损（刀片钝化、链条松、螺栓松动、滤网堵塞）。

反问模板统一为"是哪一款工具？具体表现是没反应 / 自动停机 / 力度不足 / 异响 / 震动？"——既收集了后续排查所需的信息，又避免了在信息不足时给出可能有害的错误指导。

3.5 澄清追问机制

当仅有弱特征命中（置信度不足）时，系统不猜答案，而是用当前语种反问以补齐信息，并把连续未命中计数（missCount）纳入上下文：连续两次未命中即引导转人工，避免用户陷入"反复问、反复答不上来"的死循环。

3.6 转人工工单

转人工由复合规则判定，而非固定短语表：

(人工对象词 ∨ 服务渠道词) ∧ (联系动词 ∨ 请求词)

例如"人工 / 真人 / 客服 / 专员"、"hotline / help desk"、"sprechen / verbinden"、"转接 / 联系 / 对接"、"quiero / por favor"、"vorrei / per favore"、"ik wil / graag"、"quero / por favor" 等 8 语种词族，与连接词组合命中。转人工时系统生成结构化工单（工单号形如 GC-XXXXXX），附带用户问题、已识别意图与品类、已给建议摘要，并给出等待期自助路径。

为什么要改成复合规则 初版采用"8 语种各 6–9 条固定短语"的白名单表，在 32 条真实问法探针上仅 43.8% 触发率——像"我想找真人聊一下""Pásame con un asesor"这类自然表达全部漏判。改为复合规则后，同一探针集触发率升至 100%。这一改动已在《应用效果说明》第 5.1 节以"改进前后对照"形式公开。

3.7 寒暄与情绪路由

寒暄（问候 / 致谢 / 告别）与负面情绪被识别为独立通道：不进入业务知识库检索，不污染 missCount 与故障上下文，因此"谢谢"不会被误当作新问题开启一轮排查。情绪识别命中后，系统先输出共情语句再给方案（8 语种各自独立的共情文案），若仍无有效意图，则主动提供人工出口。

3.8 演示模式与标注浮层

顶栏「▶ 演示模式」提供 4 个预设场景（英文草坪机故障排查 / 法语修枝剪选型 / 德语链锯养护与配件 / 中文综合售后），支持慢 / 中 / 快三档播放速度，并以浮层标注演示者需要强调的观察点。该模式与真实交互走同一条渲染链路，不存在"演示专用逻辑"，因此演示所见即产品所得。

5.3 工作流规范状态机

为保证不同语种、不同品类的出口行为一致，引擎遵循统一的工作流规范，每个状态只允许四类出口：直答（DIRECT）、追问（CLARIFY）、转人工（HANDOFF）、兜底（FALLBACK）。

规范要点 ① 寒暄通道不进入知识库检索，不累加未命中计数；② 情绪命中时先安抚再给方案；③ 只有强特征命中才允许直接出答案，弱特征一律转 CLARIFY；④ HANDOFF 与 FALLBACK 两条路径互不重叠，工单一旦生成即携带完整上下文摘要。

十、演进路线

十一、原创性说明

本作品的原创性体现在三个方面，均可核验：

  1. 代码原创性：全部源码为团队自研，采用零依赖单文件架构（不使用任何第三方前端框架或 UI 库），Git 提交历史完整保留，可通过 git log 逐版本核对演进过程。
  2. 数据原创性：意图词表（48 张表 / 1939 条）与知识库（241 条 × 8 语种）为团队逐条撰写与校对，其中知识内容参考了厂商公开的产品手册与安全规范（如 ANSI Z87.1 护目镜标准、CE 认证要求），并在文中标注来源依据；测试用例为中/英/法/德/西/意/荷/葡母语客服的真实问法，未使用引擎内置关键词表的直译版本。
  3. 品牌与型号声明：GreenCraft Pro 为本项目自建的演示品牌，文中出现的 GC-480E、LM2100SP、P-500、GC-2000PW 等型号及 AB2100、GC-520-CH-18 等料号均为演示虚构，不对应任何真实厂商产品，避免误导评委与观众。
关于知识内容的引用边界 本作品的知识条目为基于公开产品资料整理的示例性内容，用于演示系统的检索与答复机制，不构成任何产品的官方维修指引。实际部署时必须由客户以自家维修手册替换——这在《落地可行性》章节的部署形态中已写明。

十二、结语

GreenCraft Pro 解决的是一个边界清晰、需求真实、却长期被多语种人力成本卡住的问题。我们没有把"AI"理解为必须调用大模型，而是把它理解为让每一条售后结论都可核验、让每一次判断都可追溯、让每一个数据都不出用户设备。在此基础上，它已经是一套可运行、可复现、可离线部署的完整系统：8 语种、10 品类、6 类意图、241 条知识条目、1939 条意图词条，352 条真实多语问法上的意图与品类识别准确率均为 100%，一次解决率 98.6%，三类流程探针触发率均为 100%，单次决策 0.05 毫秒，零外部请求。

我们清楚地知道边界在哪里：知识库仍是百条级小样本，跨语种输入仍需手动切换语种，IoT 与大模型仍在路线图上。因此我们把下一步押在两件事上——把知识库做到万级，以及让一次真实的企业试点提供第一批 CSAT 真实数据。前者决定这套系统能服务多深的行业，后者决定我们能不能用真实数据而不是测算值说话。
